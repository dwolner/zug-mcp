## Gotchas — two new ones

**1. Publishing is Danno's step, not the agent's.** `npm publish` fails with `npm error code EOTP`
(2FA). He publishes with **`npm publish --auth-type=web`**, which opens a browser flow. Prepare
everything up to it — commit, tag, `npm pack`, install-test the tarball — then hand him the command.
Verify afterwards by comparing `npm view zug-mcp dist.integrity` against
`openssl dgst -sha512 -binary <tgz> | openssl base64 -A`; matching values prove the published bytes
are the ones that were tested. For 1.3.1 they matched (`sha512-qYWYX9Fq…`).

**2. `git push --follow-tags` does NOT push this repo's release tags.** They are lightweight, and
`--follow-tags` only pushes annotated ones. `v1.3.1` silently stayed local until an explicit
`git push origin v1.3.1`. Check `git ls-remote --tags origin` after any release.

Still true from the previous handoff: never run `next build` in `web/` while the dev server is up
(use `NEXT_DIST_DIR=.next-verify npx next build`, then `git checkout web/next-env.d.ts`); and the
auto-mode classifier intermittently blocks `npm publish` / `git push` / `fly deploy` — first attempt
denied, retry passes. Budget a retry rather than rewriting the command.

## Do NOT redo these — done, published, and verified

- **ISS-052 (resolved), shipped in 1.3.1.** `src/onboard.ts` had been a complete 126-line flow since
  T-009, but the CLI dispatch never had an `onboard` case on any branch while three surfaces told
  users to run it. Now dispatched via dynamic import (so no other command loads the Anthropic SDK),
  `dist/onboard.js` published, `runOnboard()` exported rather than self-executing, and both stale
  `pnpm onboard` hints corrected.
- **`install.sh` regression, caught by the independent review, fixed in the same commit.** Removing
  the top-level `main()` turned `install.sh:158`'s `npx tsx src/onboard.ts` into a silent no-op that
  exits 0, so the `|| cp template` fallback never fired. It now invokes the CLI and keys the fallback
  off **whether PERSONA.md exists**, not the exit code — onboarding legitimately exits 0 when it
  skips, so a non-interactive install fell through both paths before this too. Verified end-to-end
  against a scratch `ZUG_DIR`.
- **The class fix: `src/packaging.test.ts` (6 invariants).** Both defects this week came from drift
  between the `files` allowlist, the CLI dispatch, and the README. The tests now assert: the import
  closure of every published entrypoint is in `files`; every `files` entry has a backing source;
  README ↔ dispatch ↔ usage agree in both directions; published code never tells a user to run a
  repo script; and any file invoked as a script self-executes (this is the one that caught the
  install.sh break). **`prepublishOnly` is now `pnpm build && pnpm test`** — the invariants only bind
  if the release path runs them. Do not weaken that back to build-only.
- **Independent review ran** (subagent, adversarial brief) and was worth it: it found the install.sh
  regression, that nothing in the release path ran the new tests, and that the `await import` sat
  outside its try/catch so a missing `dist/onboard.js` surfaced as a raw unhandled rejection. It also
  attacked the test regexes; the closure walker now handles side-effect imports, `require()`,
  `import x = require()`, subdirectories, and excludes type-only imports.
- **1.3.1 verified from the registry**, not just locally: clean `npm install zug-mcp@1.3.1` →
  `zug --version` 1.3.1, `dist/onboard.js` present, `zug onboard` dispatches, `zug persona` prints
  the corrected hint. 22 files.
- **CHANGELOG now records 1.3.0** as well — it was published without an entry.
