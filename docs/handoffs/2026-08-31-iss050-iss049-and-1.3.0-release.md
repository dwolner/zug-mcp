## The gotcha list has changed — re-read this

The previous handoff said the globally installed `zug-mcp` was 1.2.0 and had none of the work.
That was true. 1.3.0 is now published, so `zug update` resolves it — but be aware what switches on:

- **`session_id` is now `sessionId`** in the MCP tool schemas (breaking rename, commit `1b2d8c0`).

**3. `fly deploy -a zug-mcp` gets blocked by the auto-mode classifier; bare `fly deploy` works.**

## Do NOT redo these — done, deployed, and verified

- **ISS-050 (resolved).** The previous handoff was wrong that synthesis never ran. It ran and
  succeeded; the reported symptom was its own leading hypothesis. THE REAL DEFECT: `handleSyncPush`
  both gated on and fed from `payload.observations` — one push's delta. Since `sync.ts` advances
  `pushSince` past everything it sends, each observation was offered to synthesis exactly once, so
  anything belonging to a failed attempt was dropped permanently. **66 observations dated
  2026-05-28 → 2026-08-31 were on the volume but absent from PERSONA.** Fixed with a server-owned
  `lastSynthesizedAt` cursor in `synthesis-status.json`; the cursor advances only after synthesis
  succeeds AND its output is written. Recovery ran: PERSONA **118 → 134 → 207 lines**, and topics
  from the lost window (Augur, Monarch, commercialization, karuna mobile) are now present.
  Idempotence confirmed — a second push with nothing pending does not re-synthesize.
- **ISS-049 (resolved).** `synthesisStatus` added to `PullResponse` / `handleSyncPull` / `sync.ts`
  pull. Verified live: the file was absent locally, and after deploy + `zug pull` it landed with
  both outcome and cursor. Also added `synthesisBacklog()` — shipping only the outcome would have
  rebuilt the blind spot, since `outcome: ok` describes the last batch and says nothing about
  observations never offered. Dashboard tile now reads "Last succeeded … 1 pending, awaiting next
  push" where it read "never run" permanently.
- **Packaging fix (e3983ec).** `dist/cli.js` required `./version-check.js` at load but it was
  missing from `package.json` `files`. Any publish from HEAD would have shipped a binary that died
  with MODULE_NOT_FOUND on every command. Latent since T-054, which landed after 1.2.0.
- **1.3.0 published.** Registry shasum `848427f4…` is byte-identical to the artifact that was
  install-tested pre-publish. Clean install from the registry verified: `zug --version`,
  `zug status`, and a `require` of `stdio.js` all work. Tagged and pushed.
- Everything the previous handoff listed under "do NOT redo" (ISS-045, ISS-046, ISS-047, ISS-048,
  T-058, T-059, T-060) still stands.

**ISS-051 (medium) — frozen-persona tile cries wolf.** Found by rendering the dashboard, not by
reading code. `consolidationGap` flags any trailing run of two equal `personaLines` snapshots, and

should scale with `observationsAccumulated` and the age of `frozenSince` — both already computed —
mirroring the age-based `BACKLOG_STALE_DAYS` judgement in the synthesis tile so the two tiles reason
consistently. Note: `growth.jsonl` reported `personaLines=131` while the file was 207, because
snapshots were written by the stale 1.2.0 client. **Re-check this after `zug update`** — part of the
discrepancy should resolve on its own.

## Caveats

- **Every plan, fix, and review this session was a self-review.** No independent lens ran. This
  mattered more than usual because it ended in a published npm artifact — **1.3.0 cannot be cleanly
  unpublished after 72 hours** (i.e. after ~2026-09-03). A second opinion is now overdue, and
  ISS-052 would be a reasonable place to spend it before publishing 1.3.1.
- The self-review did miss something real: ISS-052's original fix direction was backwards and would
  have deleted a working feature. It was caught by a four-word user question, not by the process.
- `1b2d8c0`'s `session_id` → `sessionId` rename shipped as a **minor** version. Defensible for
  schema-reading callers, but it is a break. If anything pins those parameter names, it fails on
  update.
